# 00. Scope, baseline, инварианты

**Status: Proposed · 2026-10-15 · v0.3**

## Задача

ShockingVRC 1.3.1 из upstream `egui` уже используется Nightmare и работает. Дорабатываем **эту** кодовую базу так, чтобы Nightmare мог включить встроенный сервер Remote Access и задать логин/пароль, а пользователь другого компьютера мог через LAN, VPN или публичный интернет подключиться отдельным Tauri Remote Terminal, наблюдать текущие значения и изменять доступные локальному GUI настройки.

## Кодовая точка отсчёта

- Fork: `Zaknin/ShockingVRC-Term`, default branch `egui`.
- Разработка: `feature/remote-access` от `e076bc2ede4726a976c60613031f48c0bc31e0b9`.
- Upstream default `main` **не** использовать как базу: это более раннее состояние, несмотря на имя ветки.
- Текущий Host: Windows; основное приложение `shockingvrc` (Rust + `eframe/egui`).
- Нативный удалённый клиент: Tauri 2 + Vue 3 + TypeScript, приоритет Windows.

## Что входит в scope

- Вкл./выкл. Remote Access и настройка имени пользователя/пароля в Host GUI.
- Авторизованный HTTPS + WebSocket сервис, подключённый к уже запущенному `Bridge`.
- Отображение состояния VRChat, устройств, каналов, зон и конфигурации; удалённая передача существующих GUI-команд.
- Сохранение профиля подключения на клиенте; пароль — через OS-protected storage.
- UPnP IGD для автоматического открытия TCP-порта, дополнительные NAT-PMP/PCP по возможности; ручной port forwarding как штатный fallback.
- Рабочее подключение LAN, VPN и direct WAN без обязательного стороннего relay. Терминал принимает IPv4 и DNS/DDNS уже в v1.
- **ICE/STUN/TURN и signaling/rendezvous входят в целевой scope проекта:** второй транспорт Remote API для сложного NAT/CGNAT, отдельный milestone. Его развёртывание требует публичной инфраструктуры или стороннего managed сервиса; это не функция одного STUN.
- Оптимизация запросов на отрисовку `egui` с целями 30 FPS в фокусе, 5 FPS в фоне, 0 FPS в минимизированном окне (при сохранении работы приложения).
- Автоматизированные проверки API, авторизации, сериализации, UI-паритета и регрессий.

## За пределами scope

- Изменения логики `src-core`: BLE, OSC, OSCQuery, DSP, UKF, waveform, modulation.
- Изменение Alarm и его текущих правил/пределов.
- Новые ограничения мощности, safety-features, рефакторинг очереди движка.
- Интеграция с FortiGate. Встроенный DDNS updater и ACME/CA TLS — будущие опции. Для ICE/TURN инфраструктура rendezvous/TURN в отдельных топологиях **неизбежна**, но прямой LAN/WAN доступ не обязан от неё зависеть.
- Замена локального `egui` на Tauri до успешного Remote Terminal.
- Принудительное изменение рабочего устройства или обязательная установка новой версии у Nightmare до проверки.

## Инварианты реализации

**INV-01.** `src-core` и алгоритмы воздействий сохраняются без изменений; любые исключения — отдельное согласование.

**INV-02.** Только **один** экземпляр BLE/OSC/Engine работает на Host; Tauri не запускает `CliEngine` и не подключается к устройству напрямую.

**INV-03.** Remote API выдаёт данные из существующего `Snapshot` и отправляет команды через существующий `Bridge`/`Worker`.

**INV-04.** Когда Remote Access выключен, API-порт не слушается и автоматический проброс не создаётся.

**INV-05.** Минимизация окна не останавливает Host, OSC или BLE. Закрытие приложения завершает Host и сетевой сервис как сейчас.

**INV-06.** Работа LAN/VPN не должна зависеть от успешного UPnP; ручное перенаправление порта также штатно. При использовании DDNS смена IP сама по себе не должна требовать перевыпуска pinned TLS identity.

**INV-07.** Логин и пароль обязательны в удалённом режиме; пароль не передаётся до аутентификации TLS/DTLS peer identity и не хранится открытым текстом в серверном конфиге.

**INV-08.** Обновление статуса удалённого UI и FPS `egui` не изменяют частоту выполнения `CliEngine`.

**INV-09.** Единственная семантика JSON-команд для WSS и WebRTC DataChannel; никакой логики команд внутри signaling/TURN.

## Минимальные критерии успеха проекта

1. Nightmare включает Remote Access в установленном Host, задаёт учётные данные и видит состояние прослушивания/проброса.
2. Другой Windows-компьютер устанавливает терминал, вводит адрес/логин/пароль, сохраняет профиль и подключается.
3. Удалённые изменения существующих настроек отражаются на Host, а локальные изменения — на клиенте.
4. При отключении Remote Access связь корректно прекращается; сам ShockingVRC продолжает обычную работу.
5. Через NAT с недоступным direct path подключение работает по ICE/TURN после настройки общей инфраструктуры.
6. Все 137 исходных тестов продолжают проходить; новые проверки — отдельными тестами.
