# ShockingVRC-Term v1.2 — Passwordless One-Click Pairing

**Status:** Owner-directed implementation addendum, 2026-10-16. This document extends the approved v1.1 package without editing it. The M4b Internet transport baseline remains **PARTIAL**: an owner-observed cross-network RELAY/UDP session delivered a pinned DataChannel and Snapshot for over 12 minutes; reconnect repeatability, direct Internet P2P, and some TURN behavior remain open and are not acceptance claims here.

## 1. Scope and invariants

This addendum replaces user-entered username/password authentication with a one-time Host invitation and a persistent Terminal device identity. It reuses the existing `HostIdentity`, TLS SPKI pinning, DTLS identity proof, Remote API v1 operation set, shared `SessionManager`, Direct WSS transport, ICE DataChannel transport, and one-active-session rule.

The feature does not change the ShockingVRC Engine, BLE/OSC/DSP/Alarm behavior, power limits, Worker timing, M3 repaint scheduling, the 37 Remote API operations, or the existing safety/capability gates. Pairing performs identity and authorization work only; it does not dispatch a control operation. The existing v1.1 documents and schemas remain unchanged.

## 2. Identities and persistent state

### Host

The existing Ed25519 `HostIdentity` remains the long-lived Host identity and TLS/DTLS signing key. Its private key stays in the current-user Windows DPAPI store. `server_id` and the SPKI fingerprint continue to be derived and verified as in v1.1.

The Host stores trusted Terminal public keys and labels in a versioned local file under its app-data directory. These are public keys, written by atomic replace. A running Host restart reloads this trust list. Outstanding invitations and authentication challenges are memory-only and expire; a Host restart invalidates them and all Remote Sessions.

### Terminal

The Terminal creates one Ed25519 device keypair on first pairing. Its private PKCS#8 bytes are stored only by the Windows Credential Manager for the current user, never in Vue state, profile JSON, logs, or an invitation. The public key determines a stable `device_id`.

Each saved Host profile contains routing and public identity data. A Host-signed rendezvous device grant is stored in the Credential Manager, scoped to that profile and Host fingerprint. Access tokens and resume tickets remain process-memory values and are not reused after a Host restart.

## 3. Invitation format and one-time pairing

Host creates a cryptographically random invitation id and 256-bit pairing secret. The Host stores only the secret hash with a 15-minute expiry. A single outstanding invitation per Host is sufficient; creating another replaces the previous one, and the Host can cancel it at any time. Concurrent proofs serialize through the existing `SessionManager` authorization state: exactly one successful proof can consume the invitation and add the device.

The link uses `shockingvrc://pair/<base64url-payload>`. Its signed payload contains the version, Host id, Host Ed25519 public key, SPKI fingerprint, optional direct Host address and port, rendezvous URL, non-secret STUN URLs, invitation id, pairing secret, expiry, a rendezvous routing token, and Host signature. It contains no Host registration key, TURN static secret, private key, password, or persistent API token.

The rendezvous routing token is derived for this invitation from the Host registration key, Host id, invitation id, and expiry. The pairing secret is an independent random value. On ICE, the Terminal presents only the routing token to rendezvous to open signaling. It sends the pairing secret to the Host only after validating the signed Host identity over the established DTLS channel. Direct WSS similarly requires the saved SPKI pin and signed Host identity proof before the pairing secret is sent.

The Terminal validates payload bounds, version, expiry, Host signature, Host id/public-key relationship, and fingerprint syntax before connecting. The Host verifies the challenge signature, invitation id/secret hash, expiry, and device key in one atomic authorization step. Reuse, expiry, cancellation, wrong Host identity, malformed links, and races fail closed. Secrets are not included in diagnostics.

## 4. Passwordless Remote API authentication

Direct WSS and ICE DataChannel use the same Rust API authentication flow:

1. The Terminal sends `auth.device.begin` with its device id and public key.
2. The Host sends a fresh, short-lived, single-use challenge bound to its stable `server_id`, current `server_epoch`, and request id.
3. The Terminal signs the canonical challenge transcript. For first pairing, the proof also carries the invitation id and pairing secret.
4. The Host verifies the Ed25519 signature. It atomically consumes the invitation and persists the public key on first pairing, or matches the key against its trusted-device store on later connections.
5. The existing `SessionManager` creates the same single active Remote Session and existing in-memory access/resume secrets. The Host returns a Host-signed device grant for rendezvous signaling plus the existing session result and initial Snapshot.

The challenge, proof, device grant, and pairing data are handled in Rust. Vue receives status and saved-profile summaries only. Direct WSS has already completed Host TLS SPKI and identity checks; ICE has already completed the Host identity-to-DTLS binding. Rendezvous routing is not accepted as proof of Host identity.

The REST password-login route, WSS `auth.login`, `auth.attach` password bypass, saved Terminal usernames/passwords, and Host username/password setup are removed from the active flow. Existing refresh, logout, heartbeat, resume, SessionManager replay protection, and API operation DTOs remain. A restart creates a new `server_epoch`, so an old resume ticket fails; a retained device key passes a new challenge and obtains a new session without pairing again.

If the Terminal loses the first login result after the Host has consumed the one-use invitation, it retries once with its persistent device key and no invitation. The Host permits that recovery only for the same trusted device whose earlier session is already `Reserved` after transport loss; active sessions and sessions owned by a different device remain busy.

## 5. Rendezvous behavior

Rendezvous retains Host registration authentication and ephemeral room/ICE/TURN routing. Its static per-Host Terminal invite token is no longer required. Initial pairing uses the per-invitation routing token; later joins use a Host-signed device grant bound to the registered Host identity and Terminal public key. The server verifies routing grants for signaling admission but stores neither private keys nor Remote API session state. The Host remains the sole authority for the trusted-device list and Remote Session.

The configuration reader may accept the prior `invite_token` field during local migration but does not use it to authorize new clients. Current VPS services are not changed by this task. Any future server rollout needs a separately reviewed compatibility and rollback check.

## 6. Host and Terminal UI

The existing Host left navigation and sections remain. Host Setup gains a compact `PAIRED TERMINALS` block with `Invite friend`, `Copy invitation`, `Cancel invitation`, trusted Terminal rows with `Revoke terminal`, and `Disconnect client`. Rendezvous, direct-address, and TURN settings remain in Advanced Setup. The direct address is optional; the invitation can be ICE-only when rendezvous is configured.

Terminal removes the Login/Password form and manual Host id/fingerprint/invite-token exchange. Opening a deep link or pressing `Open & Pair` after pasting starts identity verification and pairing automatically. The Connect section lists saved Hosts and provides `Connect`, `Disconnect`, and `Forget Host`. Both link paths enter the same Rust pairing function. A saved Host reconnect uses its device identity and grant. The established left navigation and all nine existing content sections remain unchanged.

The installed Windows Tauri app registers the `shockingvrc` URI scheme. Link parsing and pairing stay in Rust; Vue only submits the pasted text and renders the resulting state. The custom scheme is a convenience mechanism, not an identity trust mechanism.

## 7. Revocation and session limits

Revoking a Terminal removes its public key from the Host trust store. If it owns the active Remote Session, the existing session is kicked and its generation invalidated. A later proof with that key fails unless the Terminal presents a new valid invitation; a new invitation can re-pair the same Terminal key. `Disconnect client` ends the current session without removing device trust. Disabling Remote Access cancels invitations, stops the listener/traversal, and kicks the session as in v1.1.

The rendezvous grant authorizes only signaling admission. A revoked device may still reach the rendezvous with a previously issued grant, but it cannot authenticate to the Host, create a Remote Session, or use the Remote API. No control operation is accepted before successful device authentication.

## 9. End-to-end user flow

1. Host owner enables Remote Access. An administrator configures the optional public direct address and rendezvous profile once under Advanced connectivity.
2. Host owner selects `Invite friend`, copies the generated link, and sends it. The Host requires no further approval or PIN.
3. Terminal opens the link or pastes it and presses `Open & Pair`; it verifies the signed Host identity, establishes Direct WSS or ICE, and sends the invitation proof directly to that Host without another confirmation.
4. Host consumes the invitation once, stores the Terminal public key, and starts the existing single Remote Session. Terminal saves the Host profile and signed device grant.
5. On future use the friend selects the saved Host and presses `Connect`. After Host restart, a fresh device challenge creates a new session; no expired session ticket or password is used.
